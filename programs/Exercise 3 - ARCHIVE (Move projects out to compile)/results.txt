--------------------- 2.4 - Exception Vectors ---------------------

--------- 2.4.1 ---------
The EPCR (Exception Program Counter Register) stores the return address when an 
exception occurs, before the CPU redirects execution to the exception vector. 
This allows the interrupted program to resume after the exception has been handled.

--------- 2.4.2 ---------
The exception vectors are defined in the .vectors section at the beginning of 
crt0.s. They contain jump instructions redirecting exceptions to the common 
_exception_handler.

The _vectors table at the end of the file stores the addresses of the specific 
exception handlers. The .global _vectors directive makes this symbol visible to the 
linker, allowing other object files to reference the same table (see 2.4.4).

--------- 2.4.3 ---------
The _exception_handler saves the general-purpose registers onto the stack, identifies 
the exception type, and uses it as an index into the _vectors table to call the 
corresponding handler through l.jalr (Jump and Link Register).

The l.jalr instruction saves the return address in r9 (link register). After the 
specific handler finishes, the compiler-generated return instructions, typically 
including l.jr r9, allow execution to resume in _exception_handler.

The _exception_handler then restores the saved registers and executes l.rfe (Return 
From Exception), which restores the PC and SR from the exception-related registers 
EPCR and ESR, allowing the interrupted program to resume.

--------- 2.4.4 ---------
The extern keyword in exception.h declares _vectors as an array of function pointers 
defined elsewhere, without creating a new array.

The .global _vectors directive in crt0.s makes the symbol accessible to other object 
files, while extern allows the C code to reference it. The linker resolves both 
references to the same table in memory.

The linker also resolves the handler names in crt0.s to their corresponding functions 
in exception.c. If the table is writable, its function pointers can be modified at 
runtime to assign different handlers, for example:

_vectors[EXCEPTION_EXTERNAL_INTERRUPT] = my_handler;

--------- 2.4.5 ---------
The given code is :

    int *addr = (int *)0x100;
    int data;

    asm volatile (
        "l.lwz %[d], 0(%[s])"
        : [d] "=r" (data)
        : [s] "r" (addr)
    );

This can generate 4 exceptions : 
 - Alignment Exception: Occurs when the address is not aligned to a 4-byte 
 boundary (e.g., addr = (int *)0x101).

 - Bus Error Exception: Occurs when the processor tries to access an invalid 
 memory address and the bus reports an error (e.g., an aligned address outside 
 the available memory).

 - DTLB Miss Exception: Occurs when the Data Translation Lookaside Buffer 
 (DTLB) does not contain the virtual-to-physical address translation, if the 
 data MMU is enabled.

 - Data Page Fault Exception: Occurs when the memory access violates page access 
 permissions or the required memory mapping is invalid, if the data MMU is enabled.


Purpose of volatile:
The volatile keyword prevents the compiler from removing or optimizing away the 
inline assembly instruction, even if its output is not used. This ensures that the 
memory access is actually performed, allowing the exception to be triggered.

--------- 2.5.3 ---------
The EPC points to the instruction following the syscall. Since OpenRISC instructions 
are 4 bytes long, the syscall instruction is located at EPC - 4.

- First syscall: 0x200000AA -> l.sys 0xAA
- Second syscall: 0x200000E0 -> l.sys 0xE0

The EPC increases from 0x23C to 0x240 (4 bytes), confirming that the two syscalls are 
consecutive.

customize exception handling without modifying the support code.
